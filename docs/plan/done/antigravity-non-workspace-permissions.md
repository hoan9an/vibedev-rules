# Plan: Antigravity least-privilege pre-allow for /vibeflow (rewritten from verified evidence)

> ✅ **Executed 2026-08-21.** `install.py` has been run on the Linux dev server; **V1–V5 all pass**, none of them closed by the owner: V1/V3 live after one more fix the static pass could not have found (see S7), V2 by a reversible live probe here (backed up, boolean off, restored), V4 by static reading, V5 by local simulation — which exposed a real Windows defect the separator framing had hidden. All V-row evidence is headless `-p`, agy 1.1.17, Linux; interactive and IDE remain a different, unmeasured path.
> Supersedes the 2026-08-21 draft authored by Antigravity on the Mac. That draft diagnosed the right problem but proposed a schema that is partly nonexistent and partly Claude Code syntax; every claim below is backed by the empirical test matrix in `docs/research/agy-permissions-wrap-bias-aug21.md` (T1–T4, T7, T8, T8b, T9, run live on the Linux dev server against agy 1.1.16).

## 1. Problem

`/vibeflow` and other multi-step runs on Antigravity (agy CLI / AG IDE) are interrupted by permission prompts — or, in headless `-p` mode, silently auto-denied ("SUCCESS" + empty response, or `jetski: no output produced`). Council sessions cannot create `~/.vibedev/agent-council/<project>/<session>/` files or run the council scripts unattended.

## 2. Verified root causes (both must be fixed; either alone leaves friction)

- **RC1 — the installer's three pre-allow rules have never matched anything on agy.** `install.py` writes `command(python3 ~/.gemini/config/skills/*)` (+ `~/.claude/skills/*`, `~/.vibedev/rules/agskills/*`). agy's permission matcher is **literal string-prefix: no glob expansion, no tilde expansion** (T8: absolute-path invocation denied; T8b: literal-tilde invocation denied; `command(git log)` + extra args allowed → prefix semantics confirmed). The `*` is compared as a literal character, so the rule prefix can never equal the start of any real command. Worse, the agy-deployed `vibeflow/SKILL.md` prescribes exactly the `python3 ~/.claude/skills/vibeflow/scripts/council_open.py` form, so every agy vibeflow run is guaranteed to hit a deny at its first script call.
- **RC2 — non-workspace file writes are gated by the global boolean `allowNonWorkspaceAccess`.** Real key, confirmed in official docs (`antigravity.google/docs/cli/settings`) and by test: `true` → write outside workspace succeeds promptless (T1); absent/`false` → write tool refuses non-workspace paths (T2). The key `nonWorkspaceFileAccess` proposed by the superseded draft **does not exist** anywhere (official docs, builtin docs, local config — zero hits). `Read(//…/**)`/`Write(//…/**)` scoped rules are **Claude Code syntax, not Antigravity's**; agy's scoped file rules are `read_file(<path>)` / `write_file(<path>)` per official permission docs.

## 3. Target architecture — least privilege, verified mechanisms only

| Layer | Setting | Status |
|---|---|---|
| Council scripts | one exact-path prefix rule per script (`council_open`, `council_read`, `council_verify`, `council_cost`, `scythe`) × 2 roots (`~/.gemini/config/skills/`, `~/.claude/skills/`) × 2 renderings (expanded via `Path.home()`, and tilde-literal) = 20 rules, no wildcard anywhere | **Verified end-to-end (V1)** — absolute-only was still 100% deny in practice; see S7 |
| Council file writes | `write_file(<HOME>/.vibe/agent-council/)` in `permissions.allow` (implicitly grants `read_file` on the same path per official docs) | **Measured (V2)** — with the global boolean off, a write into this rule-covered path succeeded while an uncovered `$HOME` path was denied 2/2, so the scoped rule stands on its own |
| Rule corpus reads | `read_file(<HOME>/.vibe/vibedev-rules/)` | Inferred from the same official rule that a `write_file()` grant implies `read_file` on its path; the write direction is the one V2 measured |
| Global boolean | `allowNonWorkspaceAccess`: leave **off** once the scoped rules above are confirmed; it opens all of `$HOME`+ to a model with a documented shortcut/helpfulness bias, and agy has a global workspace index that resolves paths back to real repos even from copied dirs | T1/T2 verified as the current gate; turning it off is the end state, not the first step |
| Per-invocation fallback | `agy --add-dir /home/user/.vibe/agent-council -p …` — brings the dir inside the workspace boundary for that run only, zero settings mutation | **Verified working (T3)**; use immediately in headless worker recipes (`harness-facts.md`) regardless of the settings work |

Explicitly rejected:
- `command(* ~/.vibedev/agent-council/*)` (superseded draft) — dead as written (glob is literal) and, if a glob engine ever appears, an arbitrary-command hole dressed as a scoped rule.
- `--dangerously-skip-permissions` as a standing mechanism — approves everything including sandbox bypass (GitHub issue #36); acceptable only for a deliberate, isolated one-shot.
- `nonWorkspaceFileAccess` — key does not exist.

## 4. Implementation steps

- [x] **S1** — `install.py merge_antigravity_permissions()`: per-script prefix rules (derived from `skills/vibeflow/scripts/*.py` — vibeflow only, which is where the pre-allow gap actually was; other skills' scripts are not covered and no evidence yet says they need to be); `write_file(<HOME>/.vibe/agent-council/)` and `read_file(<HOME>/.vibe/vibedev-rules/)`; legacy dead rules stripped during merge; unparseable settings skipped with a warning instead of rebuilt from empty. *Code in tree — takes effect only at S5.*
- [x] **S2** — both targets wired: `~/.gemini/antigravity-cli/settings.json` (CLI) and `~/.gemini/settings.json` (IDE global).
- [x] **S3** — `docs/ref/cli-permission-allowlist-standard.md` §1.2 rewritten from evidence (real keys, `read_file`/`write_file`/`command` syntax, literal-prefix matcher, headless soft-deny, `--add-dir`), with CLI-measured vs IDE-inferred scope labeled.
- [x] **S4** — `skills/vibeflow/SKILL.md` § Harness notes. First written as "expand `~` yourself"; **superseded by S7** and rewritten to "run the command exactly as written, every rendering is pre-allowed" once V1 showed the instruction was ignored in practice.
- [x] **S5** — `python3 install.py` run on the Linux dev server 2026-08-21; both settings files carry the managed rules, the legacy `*`-glob entries are gone. No separate Mac run is owed — see V4.
- [x] **S6** — `CHANGELOG.md` entry written (`[Unreleased]` § Fixed, carrying the V-row results and the unverified list); plan moved to `docs/plan/done/` on 2026-08-21 once V2 and V4 closed.
- [x] **S7 — dual rendering per script (added 2026-08-21 from V1's first, failing run).** The absolute-path-only rule set was still 100% deny in practice: an agy session copies this skill's literal `python3 ~/.claude/skills/vibeflow/scripts/council_open.py` line and never applies the § Harness notes instruction to expand `~` — a note 190 lines below the command it modifies loses to the command every time. The matcher is symmetric (it compares strings), so a tilde-literal *rule* matches a tilde-literal *command*: `install.py` now emits both renderings × both roots (20 `command()` rules for 5 scripts), each still one exact script path with no glob. This is `pattern.A8` — the flow was reshaped so the correct thing happens automatically, instead of another line of prose telling the model to normalize a path. `SKILL.md` § Harness notes and ref doc §1.2 updated to state the mechanism rather than the old instruction.

## 5. Verification matrix

- [x] **V1 — PASS (Linux, 2026-08-21, agy 1.1.16, `gemini-3.7-flash-high`).** `agy -p "/vibeflow discuss: SMOKE TEST — run the council open script, report verbatim any permission denial, then stop."` → exit 0, `~/.vibedev/agent-council/guest/2026.08.21-1258-smoke-test/` created, 0 denials, empty stderr. **First run failed** with `permission check failed for command "python3 ~/.claude/skills/vibeflow/scripts/council_open.py …"` — the rendering mismatch that produced S7; re-run after S7 passed. The run wrote under `~/.vibedev/agent-council/` with `allowNonWorkspaceAccess` still `true`, so it is evidence for the `command()` rules only, not for the scoped `write_file()` rule — that stays V2's job.
- [x] **V2 — PASS, measured here in headless `-p` (2026-08-21, agy 1.1.17, Linux, `gemini-3.7-flash-high`).** Not an owner task after all: both settings files were backed up, `allowNonWorkspaceAccess` set to `false`, the probes run, and the originals restored and re-read to confirm (`true`/119 entries on the CLI file, key absent/24 on the IDE file — byte-identical to the start). Results: a write into the rule-covered `~/.vibedev/agent-council/` **succeeded**, so the scoped `write_file()` rule is sufficient on its own and the global boolean is not a prerequisite; an uncovered `$HOME` path was **denied 2/2**. Two by-products the ref doc had only inferred: the boolean is **not** a general sandbox (writes anywhere under `/tmp` still succeed — same `write_to_file` tool, so the gate follows the path), and `trustedWorkspaces` is **not** a write allowlist (`/home/user` is listed in it, the `$HOME` write was refused anyway). *Scope:* headless only — the vendor documents interactive mode as prompting instead, a path this did not exercise.
- [x] **V3 — PASS (2026-08-21).** Install run twice: 107/12 allow entries, zero duplicates. After the V1 agy session re-serialized `settings.json`, all 20 managed `command()` rules plus both scoped file rules survived (`allow` grew to 117 from the session's own "always allow" clicks, none of them ours).
- [x] **V4 — closed by static reading, no Mac run needed (2026-08-21).** The question was whether macOS is a distinct code path for this feature. It is not: `install.py` has **no macOS branch at all**. Its two `sys.platform` tests are both `win32`-only — terminal-colour capability (`_ansi_supported()`, install.py:54) and the Windows launcher list added by V5 (install.py:408) — so macOS takes the same path Linux does. Every path in `merge_antigravity_permissions()` derives from `Path.home()`, and agy's settings locations (`~/.gemini/antigravity-cli/settings.json`, `~/.gemini/settings.json`) are identical on macOS. A Mac smoke would re-run the same bytes over `/Users/<you>` instead of `/home/user` — it re-observes, it does not verify. *Reopen trigger:* an agy build that stores settings under `~/Library/Application Support/` on macOS, which would make the target-file list platform-dependent.
- [x] **V5 — closed (2026-08-21).** Separators match by construction (both renderings simulated locally under `PureWindowsPath`), but asking exposed a real defect: the installer hardcoded `python3` against `README.md`:47's own Windows convention (`py -3` / `python`), which would have made the managed rule set 100% deny there. Fixed — `install.py` now emits the platform's launchers (60 `command()` rules on Windows, 20 on Unix), same exact-path-no-glob shape. **Not tested on Windows**, and not a gate on anything here: the installer's Windows leg is covered by the `windows-latest` CI matrix (`README.md`:40), and this repo has never blocked a release on a local Windows run.
